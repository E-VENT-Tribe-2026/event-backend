# Database Migration & Team Contribution Guidelines

This guide defines the mandatory standard operating procedure (SOP) for making database changes and submitting SQL migration Pull Requests in `event-backend`.

---

## 1. Background & Context (Issue #181 Post-Mortem)

In previous sprints, ad-hoc table alterations were executed directly against the remote Supabase database instance without committing corresponding schema migrations to version control.

### Consequences:
1. **Broken Fresh Environments**: When initializing a clean PostgreSQL/Supabase database (e.g., local developer machine, test runner, staging), `supabase db push` failed immediately because migrations attempted to alter or enable RLS on tables (`profiles`, `events`, `friend_requests`, `friendships`, `event_chats`) before they had been created.
2. **Missing Schema Elements**: Code relying on columns like `notifications.related_user_id` failed at runtime because migrations creating the columns were executed out of order or omitted entirely.
3. **Migration Deadlocks & Collisions**: Duplicate constraints and indexes caused fatal errors when applied across multiple environments.

To avoid this, **ALL database changes MUST be committed as version-controlled migration files in `supabase/migrations/`**.

---

## 2. Core Rules for Migration PRs

### Rule 1: Never Execute Schema Changes Without a Migration Script
- Do **not** manually create tables, columns, constraints, or policies in Supabase Studio unless you immediately capture the DDL into a migration script and commit it.
- Teammates must open a PR with the migration script before or simultaneously with backend code that depends on it.

### Rule 2: Chronological Timestamped Filenames
Supabase applies migrations in strict alphabetical/lexicographical order.
Every migration file in `supabase/migrations/` must follow:
```
YYYYMMDDHHMMSS_brief_snake_case_description.sql
```
- Example: `20261101140000_add_event_organizer_badge.sql`
- Generate via Supabase CLI:
  ```bash
  npx supabase migration new your_feature_name
  ```

### Rule 3: Idempotency is Mandatory
Every statement in a migration must be safe to run against:
- A completely fresh/empty database.
- A database that already partially or fully has the changes applied.

#### Required Idempotency Patterns:
- **Tables**: Use `CREATE TABLE IF NOT EXISTS public.table_name (...)`.
- **Columns**: Use `ALTER TABLE public.table_name ADD COLUMN IF NOT EXISTS column_name data_type ...`.
- **Row-Level Security**: Use `ALTER TABLE IF EXISTS public.table_name ENABLE ROW LEVEL SECURITY;`.
- **Policies**: Drop first or wrap safely:
  ```sql
  DROP POLICY IF EXISTS "Policy name" ON public.table_name;
  CREATE POLICY "Policy name" ON public.table_name FOR SELECT USING (true);
  ```
- **Indexes**: Use `CREATE INDEX IF NOT EXISTS idx_name ON public.table_name (...);` or unique check DO block.
- **Constraints**: Wrap in a `DO $$` block:
  ```sql
  DO $$
  BEGIN
      IF NOT EXISTS (
          SELECT 1 FROM pg_constraint WHERE conname = 'constraint_name'
      ) THEN
          ALTER TABLE public.table_name 
              ADD CONSTRAINT constraint_name CHECK (...);
      END IF;
  END;
  $$;
  ```
- **Seed Data**: Always include conflict resolution:
  ```sql
  INSERT INTO public.table_name (...) VALUES (...)
  ON CONFLICT (id) DO NOTHING;
  ```

## 3. Pull Request Submission Checklist

When opening a PR that includes database changes, verify the following in your PR description:

- [ ] Migration file placed in `supabase/migrations/` with correct timestamp format.
- [ ] Uses `CREATE TABLE IF NOT EXISTS` or `ADD COLUMN IF NOT EXISTS`.
- [ ] Foreign keys reference valid, existing tables in prior migrations.
- [ ] RLS is explicitly configured with appropriate read/write policies.
- [ ] All constraints use `DO $$ BEGIN IF NOT EXISTS (...)` guards.
- [ ] Verified locally using `supabase db reset` or sequential migration test.
- [ ] Corresponding Pydantic models and backend services in `app/` are included in the same PR or marked as dependency.

## 4. Migration Boilerplate Template

Copy and adapt this template when creating new migrations:

```sql
-- =============================================================================
-- Migration: YYYYMMDDHHMMSS_<feature_name>.sql
-- Issue: #<issue_number>
-- Description:
--   Brief summary of schema changes and why they are needed.
-- =============================================================================

-- 1. Table creation (if new)
CREATE TABLE IF NOT EXISTS public.example_feature (
    id BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    user_id UUID NOT NULL REFERENCES public.profiles(id) ON DELETE CASCADE,
    title TEXT NOT NULL,
    status VARCHAR DEFAULT 'active',
    metadata JSONB,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 2. Indexes
CREATE INDEX IF NOT EXISTS idx_example_feature_user_id 
    ON public.example_feature (user_id);

-- 3. Constraints (conditional check)
DO $$
BEGIN
    IF NOT EXISTS (
        SELECT 1 FROM pg_constraint WHERE conname = 'example_feature_status_check'
    ) THEN
        ALTER TABLE public.example_feature 
            ADD CONSTRAINT example_feature_status_check 
            CHECK (status IN ('active', 'archived', 'deleted'));
    END IF;
END;
$$;

-- 4. Row Level Security
ALTER TABLE IF EXISTS public.example_feature ENABLE ROW LEVEL SECURITY;

DROP POLICY IF EXISTS "Auth read access for example_feature" ON public.example_feature;
CREATE POLICY "Auth read access for example_feature" 
    ON public.example_feature 
    FOR SELECT TO authenticated 
    USING (true);

DROP POLICY IF EXISTS "Auth write access for example_feature" ON public.example_feature;
CREATE POLICY "Auth write access for example_feature" 
    ON public.example_feature 
    FOR ALL TO authenticated 
    USING (auth.uid() = user_id);
```
